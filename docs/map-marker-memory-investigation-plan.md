# План исследования и устранения утечек map-маркеров

## Current publication status

The historical investigation below is preserved unchanged. The current work is
a partial PR #12 follow-up based on master `020e81f`, after the PR #15 revert;
see [current correction evidence](pr12-correction-evidence.md). It adds eight
inline regression tests, with test-only process/injector fixtures and no separate
`src-tauri/tests` tree. The user explicitly dropped expanded/rare injector
restart and lifecycle work; the broader proposals below are not this PR's scope,
and PR #13's reverted architecture is not restored.

On the updated base, independent locked Cargo reruns passed **259 backend tests**,
**29 i686 Windows marker-filter tests**, and a normal backend build (**exit 0**),
with existing warnings. Historical counts below are not replaced. Earlier live
observations concern earlier versions, not validation of this correction:
**no live-game QA of this patch has been performed**. Native pool-generation
and renderer-concurrency QA remain pending; no full-lifetime safety/allocation
guarantee or ERROR #8 closure is claimed. Quarantine may stop marker updates or
leave old markers visible until native cleanup.

Статус: исследованы allocator, сериализация и обычные сценарии маркеров;
подтверждена недостаточность проверки старой ячейки по содержимому после
очистки. Синхронизация и аварийные пути ещё не закрыты. Исправления не начаты.

**Уточнение версии после экспериментов:** тестируемый EXE подтверждён как
официальный 1.27.1; исходная локальная папка содержит 1.27.0. Полное
перевыделение неизменившихся маркеров уже исправлено в 1.27.1. Перечень
кейсов ниже остаётся матрицей проверок, а не утверждением, что каждый
старый дефект присутствует в работающей версии. Перед реализацией привести
исходную базу к подтверждённому релизу, сохранив чужие локальные изменения.

## Цель и границы

Устранить потерю ресурсов в путях map-маркеров, не меняя правила фильтра,
координаты, внешний вид, TTL, условия исчезновения и уведомления.
Включить общие буферы инжектора, используемого маркерами; прочие хуки не
переписывать, но учитывать их расход в измерениях переподключения.

В 1.27 исправлено незакрытие handles `CreateRemoteThread`, а не все утечки.
Связь остальных находок с пользовательскими ERROR #8 не доказана.
Потеря адресов ячеек подтверждается кодом; общий путь освобождения allocator
разобран до HeapFree. Выполнение cleanup наблюдалось при переходе между
актами. Нельзя приравнивать любую смену географической области к очистке
или считать совпадение указателей/байтов доказательством жизни объекта.

Работаем пошагово: ассистент готовит ограниченный CE Lua-скрипт и инструкцию,
пользователь выполняет сценарий в локальной игре, вместе разбираем результат.
Каждый этап закрывается свидетельствами, а не только отсутствием падения.
Результаты записываем в этот файл под соответствующим этапом: версия/хеш
модуля, сценарий, наблюдение, путь к логу, вывод и оставшиеся вопросы.

Все модули: machine=014C, optional-header magic=010B (x86 PE32).
Разбор присланных пользователем байтов `D2Client+5F6B0` до `+5F758`:

- Счётчик выдачи ячеек читается/увеличивается по `D2Client+11C1BC`.
- Голова списка блоков читается по `D2Client+11C1B8`.
- Для неотрицательного счётчика индекс блока = count / 512, ячейки = count % 512.
- Блок содержит 512 ячеек по 20 байт (`0x2800`) и next-pointer по `+0x2800`.
  При отсутствии нужного блока функция запрашивает `0x2804` байт, обнуляет
  блок и присоединяет к списку. Возвращаемая ячейка также обнуляется.
- В этой функции нет возврата отдельной ячейки или уменьшения счётчика.
  Отвязка от дерева сама по себе не меняет показанную структуру allocator.

Это подтверждает блочную выдачу, но не время освобождения/переиспользования
блоков другими функциями.

### Функция очистки: разбор байтов пользователя

Read-only поиск абсолютных операндов в D2Client дал 7 совпадений без
пропущенных страниц. Это не исключает косвенных обращений или кода других DLL.
Получено тело `D2Client+5F300`:

- Читает текущий слой из `+11C1C4`; при NULL сразу возвращается.
- `xor edi,edi` задаёт ноль, ESI получает голову списка из `+11C1B8`.
- Для каждого блока сохраняет его адрес в ECX и заранее читает next по
  `+0x2800`, затем вызывает `D2Client+BF86` (call расположен по `+5F32A`).
  EDX получает `D2Client+D537C`; в стек передаются 0 и `0x51E`.
  Это похоже на allocator API с диагностическими file/line, но цель ещё не разобрана.
- После обхода обнуляет глобальные head/count и корни текущего слоя
  по `+08`, `+0C`, `+10`, `+14`.

Обход очистки использует список блоков allocator, а не дерево отдельных
AutomapCell. Отвязка ячейки от дерева не скрывает её блок от этого обхода.
Нужно подтвердить, что вызов `+BF86` действительно освобождает блоки;
пока не утверждать постоянную утечку до завершения Game.exe.

### Разрешение вызова очистки в Fog

Пользовательский снимок: `D2Client+BF86` содержит `FF 25 44 EE B7 6F`.
IAT slot `6FB7EE44` разрешился в `Fog.Ordinal10043` по `6FF6CCF0`
(`Fog+1CCF0` при базе `6FF50000`). Обёртка сохраняет входной ECX
(указатель блока) в локальный слот, передаёт его адрес в ECX, обнуляет EAX
и выполняет `call` по `Fog+1CD01` во внутреннюю функцию `Fog+1B0C0`.
После возврата обёртка устанавливает EAX=1 и делает `ret 8`.

### Внутренний allocator Fog: тело `+1B0C0`

По байтам, присланным пользователем:

- При EAX=0 выбирается глобальный контекст `Fog+4AF94`.
- Для ненулевого освобождаемого указателя вызывается lookup `Fog+1A9F0`.
- В распознанном пуле вычисляется индекс элемента; проверяется бит занятости,
  затем бит очищается (`+1B14E`) и уменьшается счётчик по `[ebx+8]`
  (`+1B150`–`+1B15D`). Вызывается дополнительная функция `Fog+1AB60`.
- Для нераспознанного/неподходящего указателя вызывается `Fog+1AA80`
  из `+1B10E` либо `+1B184`.

Это подтверждает семантику возврата элемента в allocator для основной ветки,
но ещё не устанавливает, по какой ветке проходят блоки automap размером
`0x2804`, и не требует немедленного уменьшения Private Bytes процесса.

### Fallback `Fog+1AA80`: реестр выделений

Присланное тело вычитает 4 из входного указателя, вычисляет bucket через
остаток деления на `0x3FF`, ищет блок в цепочке реестра контекста по
`+0x7AC + bucket*4` и при нахождении исключает его из цепочки.
Импорты подтверждены CE: `+1AAAD` → `ntdll.RtlEnterCriticalSection`,
`+1AADB` → `ntdll.RtlLeaveCriticalSection`. После выхода из секции,
в том числе если запись не найдена, передаёт `pointer-4` в call по
`Fog+1AAE2`; относительное смещение разрешается в `Fog+1FAD`.

Наличие блокировки внутри allocator не доказывает безопасность конкурентного
изменения automap-дерева или его внешнего счётчика выдачи.

### Конечная функция освобождения подтверждена

Пользователь прислал тело `Fog+1FAD` и хвост до `+201C`.
Функция проверяет NULL, имеет отдельную small-block ветку, а общий путь
по `+2009` подготавливает аргументы и по `+2012` вызывает импорт:
`FF 15 0C 51 F7 6F`, IAT `6FF7510C` → `76A141B0 (KERNEL32.HeapFree)`.
Передаются указатель, flags=0 и heap из глобальной переменной `Fog+58280`.

Таким образом, общий путь cleanup подтверждён до системного освобождения:
`D2Client+5F300` → `D2Client+BF86` → `Fog.Ordinal10043` → `Fog+1B0C0`
→ fallback `Fog+1AA80` → `Fog+1FAD` → `HeapFree`.
Основная pool-ветка возвращает элементы собственному allocator Fog.
Конкретная ветка для каждого automap-блока и успешный результат HeapFree

### Анализ безопасного места выполнения: ограничения

В исходниках релиза повторно проверены injection.rs, offsets.rs и
dps_hook/trampoline.rs. Windows `new_automap_cell` выполняется через
CreateRemoteThread; mutex инжектора не синхронизирует эти операции с
движком. Linux использует ptrace-вызов, но сам по себе захват произвольного
потока также не доказывает безопасную точку для automap.

Существующие hooks не дают установленного места commit:

- DPS trampoline вызывается при stat-write, а не гарантированно каждый
  игровой тик; обработка события HP не доказывает отсутствие teardown.
- Tooltip hook зависит от обработки tooltip, не покрывает пустой экран/idle.
- Loot visibility predicate не имеет доказанного порядка относительно
  обхода и очистки automap. Не добавлять лишнюю связь маркеров с DPS.

Условное направление (ещё НЕ утверждённый протокол реализации): Rust
сохраняет BFS/фильтрацию и формирует желаемый набор значений, без передачи
старых игровых указателей. Единственный обработчик внутри игры выполняет
allocation/reuse/link/unlink в подтверждённой безопасной точке; инвалидирует
все retained/free-cell адреса до очистки их поколения. IPC должен иметь
определённую публикацию целого сообщения/ack и ограниченный объём, не
полагаться на предполагаемую атомарность произвольного WriteProcessMemory.
Остановка требует подтверждённого отсутствия потребителей, не задержки 50 мс.
Повторная проверка generation без сериализации всё ещё допускает TOCTOU.

Следующий минимальный пользовательский шаг: read-only bytes двух окон:

1. `D2Client+44200`, длина `80` hex — вокруг кандидата GameLoop+44230.
2. `D2Client+62690`, длина `C0` hex — вокруг кандидата automap+626C9
   и уже изученного selector+62710.

Не ставить точки/патчи до разбора фактических байтов. Если окно содержит
MXL detour, разбирать его реальную цель, не восстанавливать байты vanilla.
После идентификации кандидат потребует ограниченной трассы порядка/потока,
работы при открытой и закрытой карте, отсутствия re-entry/concurrent cleanup
и прохождения transitions/exit/re-entry. Одно совпадение thread id или
один спокойный stack snapshot не доказывают сериализацию всех путей.

Скептическая проверка архитектуры: **NO-GO для внедрения фикса reuse сейчас**.
Нужен подтверждённый порядок с draw/save/cleanup/restore и корректная
инвалидация команд. Подготовка регрессионных сценариев возможна, но не
объявлять выбранной безопасную функцию до следующего свидетельства.

### Ошибка диагностического callback и исправленный инструмент

Старый inline-скрипт после mapFrameProbeStart выдавал повторяющееся
`attempt to index a nil value (upvalue 'r')` на первом r.hits, до pcall.
Пользователь остановил спам через Finish. Это ошибка диагностического
скрипта; из неё нельзя делать выводы о состоянии игры.

Публичный код CE хранит callback через luaL_ref, а не доказанное клонирование
без upvalues. Точная причина nil в CE 7.6 не установлена; не объяснять её
«обычным поведением Lua», сборщиком мусора или потерей callback без свидетельств.

Исправленный инструмент: [ce-map-frame-probe.lua](ce-map-frame-probe.lua).
Именованный глобальный callback не захватывает локальный run. Все обращения
к run внутри pcall; ошибка capture снимает нашу точку, сохраняет сообщение
и выполняет попытку continue. Ошибки снятия/continue видны в отчёте.
Скрипт не пишет игровые данные и не меняет production Rust.

Локальная проверка через Fengari (Lua 5.3) с CE API doubles:

- Негативный контроль старой формы с nil run: проверка снятия/continue падает.
- Новый callback имеет только _ENV как upvalue.
- Пройдены нормальные 3 hits/автоснятие/второй режим/сохранённый отчёт;
  потеря activeRun; ошибка чтения; неверный EIP; ручное снятие без hits;
  сохранение чужой точки; отказ по несовпадению байтов; ошибка установки.
- Это проверка Lua-логики, НЕ эмуляция CE debugger или воспроизведение
  первопричины nil upvalue. Нативный запуск нового варианта ещё требуется.
- Lua LSP не установлен; синтаксис и выполнение проверены интерпретатором.
  Временные harness и журнал удалены после проверки.

Первоначальная инструкция запуска v2 ОТОЗВАНА после следующего нативного
сбоя. Ни старый mapFrameProbeStart, ни v2 mapFrameTraceStart не запускать.

### Условия протокола и следующий узкий gate

Скептическая проверка: можно готовить чистые state-machine/regression tests,
не включая запись в живой игре. Перед выбором callback-слота для native
подключения выяснить, кто переписывает +1197E4 после начальной установки.

Требования к реализации, не заменяемые дополнительными снимками:

- Команда содержит собственную неизменяемую копию значений, без старых
  указателей на игровые ячейки. Существующие TTL/правила сохраняются.
- Admit/reconcile/cleanup сериализованы. Generation закрывается **до
  первого освобождения** на входе соответствующего пути, не только на
  исследованном эпилоге +5F350. Старые команды и free-list инвалидируются.
- Все потенциально reentrant вызовы и выход/повторный вход учитываются;
  same-thread observations не являются доказательством невозможности гонок.
- Если используется слот: полностью подготовить обработчик до публикации;
  только native atomic compare/exchange с ожидаемым original, не предполагать
  атомарность WriteProcessMemory. Чужое значение не перезаписывать.
- При снятии восстановить слот только если он всё ещё наш. Нулевой счётчик
  выполняющихся callback недостаточен: caller мог прочитать адрес до входа.
  Без доказанного quiescence код нельзя освобождать; один учитываемый resident
  блок на процесс с pass-through допустим как явное ограниченное владение,
  не как накапливающиеся потерянные выделения при каждом restart.
- Ошибки, устаревшие команды, закрытие поколения при admit, повторный адрес,
  несколько producers и частичные операции должны иметь regression tests.

Следующий пользовательский эксперимент без Lua callbacks: стандартный CE
"Find out what writes to this address" на 4 байта +1197E4. Зафиксировать
начальное значение, выполнить один ограниченный сценарий map close/open,
перехода акта, выхода в меню и повторного входа без перезапуска Game.exe.
После Stop прислать writer instructions/counts, доступные registers через
More information и конечное значение. Пустой список означает только
отсутствие замеченных writes в этом сценарии; не доказательство неизменности
слота при всех условиях. Записи могут исключить слот либо потребовать
согласования с владельцем. Не менять значение или флажок freeze.

### Переход от ручных замеров к подготовке реализации

Для проектирования модели уже достаточно фактов: callback подтверждён,
однопоточное выполнение frame/cleanup наблюдалось, поле-сигнатура после
сброса непригодна, обычное накопление и инкрементальный режим измерены.
Широкий реверс соседних функций и повторные дропы остановить.

Следующая самостоятельная работа ассистента (не выполнена этой записью):

1. Подготовить отдельную локальную базу точного релиза 1.27.1, не менять
   чужой dirty master. Сохранить текущие RE-документы отдельно от релизной базы.
2. Описать и проверить чистую модель состояний: inactive/active generation/
   invalidating/stopping; владение каждой ячейкой active/free/pending,

   команд и прерванных операций. Границы поколений не определять по совпадению
   layer/head/fSaved/sprite. Не выдавать модель за нативную проверку движка.
3. В native-адаптере решить отдельно: точку инвалидации ДО free, сериализацию

адаптера. До этого утилиту с экспериментальными native-изменениями не запускать;
